## 2. 实际开发时间线

这次开发不是一次完成的，中间经历了登录态、浏览器 profile、站点反爬和项目拆分
等问题，最终才确定两个站点不能使用完全相同的方案。

1. 最初把 AnyRouter 和 AgentRouter 放进同一个 Playwright 签到脚本，计划通过
   持久化 profile 保存登录态。
2. 实际登录时发现 OAuth、hCaptcha 和真实浏览器 Cookie 落盘存在差异。浏览器
   虽然已经显示登录成功，但脚本读取不到有效 Cookie，原因包括自动化浏览器特征

6. 恢复使用原项目脚本后，AnyRouter 又出现 `HTTP 403 / Denied by

   ESA/WAF 或代理出口限流。
7. 最后参考 `millylee/anyrouter-check-in`，将 AnyRouter 改成持久化 `session`
   Cookie 加临时浏览器 WAF 预热，再用 HTTPX 调用签到 API；AgentRouter 暂时关闭，

8. （2026-08-27）删除独立目录 `checkin-agent/`。核对确认它只是 08-26 11:28 的旧

9. （2026-08-27）修正 WAF 就绪判定：原来只等 WAF Cookie 名字出现就返回，但

10. （2026-08-27）用受控对照定位到 403 的真正原因不是 Cookie 而是**网络栈**，

    HTTPX 方案就此作废。

## 3. 最初的实现方案

最初方案把两个站点统一放进一个脚本中：

- 使用 Playwright 启动真实安装的 Edge/Chrome。
- 每个账号使用独立浏览器 profile。
- 浏览器负责访问站点、通过阿里云 ESA/WAF。
- API 请求使用浏览器上下文中的 Cookie。
- AnyRouter 调用：

```text
GET  /api/user/self
POST /api/user/sign_in
GET  /api/user/self
```

- AgentRouter 调用 `/api/user/self`，因为该站点访问用户信息接口时会触发签到。

当时的判断是：登录态保存在：

```text
data/checkin_profiles/<profile>/
```

首次使用时执行：

```powershell
python tools\daily_checkin.py --login <账号名>
```

## 4. 登录和 profile 问题

### 4.1 登录方式

AgentRouter 使用 LinuxDO 或 GitHub OAuth 登录，页面可能包含 hCaptcha。
Playwright 启动的自动化浏览器容易被识别，因此登录流程改为：

1. 使用系统中安装的真实 Edge/Chrome。
2. 通过 `subprocess` 普通启动浏览器。
3. 用户手工完成 OAuth 登录。
4. 用户正常关闭浏览器，等待 Cookie 落盘。
5. 脚本再使用 Playwright 校验 `/api/user/self`。

不使用任务管理器强制结束浏览器，因为强制结束可能导致 Cookie 尚未写入 profile。

### 4.2 独立项目尝试

为了避免影响 Bot，历史上曾将签到脚本复制到：

```text
checkin-agent/
```

该目录包含自己的脚本、配置、日志和 profile。

随后发现：

- 独立项目和原项目使用的是两套 profile。
- 在一个项目中登录，不会自动出现在另一个项目中。
- 复制 profile 只能复制当时的状态，不能解决后续登录态同步问题。
- 独立项目的 `.cmd` 不是根本问题，真正问题在 API 返回的 `403`。

当时根据用户要求，后续暂时恢复按原项目维护：

```text
tools/daily_checkin.py
tools/checkin_sites.json
data/checkin_profiles/
```

## 5. AnyRouter 的 403 问题

> 本节记录的是当时的排查过程和推测，**结论已被第 7 节推翻**。
> 真正原因不是代理出口限流，见第 7 节的对照实验。

原项目曾经出现过成功日志，例如：

```text
anyrouter-1: 签到成功
anyrouter-2: 签到成功
```

之后接口开始返回：

```text
HTTP 403
Denied by http_ratelimit
```

这说明：

- 不是 `.cmd` 调用失败。
- 不是单纯的登录失效。
- 不是只缺 `New-Api-User` 请求头。
- 当前代理出口可能触发了 ESA/WAF 限流。

同时，浏览器页面仍可能正常打开并显示已登录，这与 API 返回 403 并不矛盾。

## 6. 参考项目的关键方案

> 本节描述参考项目的做法。其中「只存 session Cookie、WAF Cookie 动态获取」
> 的认证模型本项目采用了；但它用 HTTPX 发 API 请求这一点在本机环境下不可用，
> 原因见第 7 节。**不要照抄 6.3 的 HTTPX 部分。**

参考项目：

```text
https://github.com/millylee/anyrouter-check-in
```

阅读其 `checkin.py`、`utils/browser.py`、`utils/config.py` 后，确认其 Cookie 模式如下。

### 6.1 账号认证

账号配置只需要提供登录后的 `session` Cookie：

```json
{
  "cookies": {
    "session": "SESSION_VALUE"
  }
}
```

参考项目还支持配置 `api_user`。它是请求头中的用户标识，不是登录 Cookie。

### 6.2 WAF Cookie

WAF Cookie 不要求手工配置，而是每次运行时用临时浏览器获取：

```text
acw_tc
cdn_sec_tc
acw_sc__v2
```

获取流程：

1. 启动临时浏览器。
2. 访问 AnyRouter 的 `/login`。
3. 等待 ESA JavaScript 挑战执行完成。
4. 从浏览器上下文读取 WAF Cookie。
5. 关闭临时浏览器。

### 6.3 API 请求

将两类 Cookie 合并：

```text
账号 session Cookie
        +
临时浏览器获取的 WAF Cookie
```

然后使用 HTTPX 请求：

```text
GET  /api/user/self
POST /api/user/sign_in
GET  /api/user/self
```

请求中保留浏览器常见请求头：

- `User-Agent`
- `Accept`
- `Accept-Language`
- `Referer`
- `Origin`
- `Sec-Fetch-*`
- `X-Requested-With`

多个账号必须串行执行，并在账号之间增加延迟，减少触发 ESA 限流的概率。

### 6.4 “只需要 Cookie”到底是什么意思

原参考项目说“只需要 Cookie”，指的是**不需要保存浏览器登录 profile，也不需要
每天重新执行 OAuth 登录**。账号真正的登录凭据只有 `session` Cookie：

```json
"cookies": {
  "session": "真实值"
}
```

但 AnyRouter 的 ESA/WAF 还会根据当前访问环境动态下发临时 Cookie。这些 Cookie
不是账号登录态，不能长期固定使用，因此脚本每次运行时用临时浏览器访问 `/login`
获取：

```text
acw_tc
cdn_sec_tc
acw_sc__v2
```

所以最终请求需要合并两类信息：

```text
固定保存：session
动态获取：acw_tc、cdn_sec_tc、acw_sc__v2
```

这仍然属于 Cookie 模式，只是把会过期、与 WAF 挑战绑定的 Cookie 交给浏览器
动态获取。若只填 `session` 而完全不经过 WAF，接口可能再次返回 `403`。

## 7. 决定性发现：403 的原因是网络栈，不是 Cookie

2026-08-27 做了一次受控对照，一次性定死原因。

**同一个浏览器上下文、同一组 Cookie、同一个代理出口、同一时刻**，只改「谁来发
这个请求」，打同一个 `GET /api/user/self`：

| 请求方 | 结果 |
|---|---|
| 浏览器页内 `fetch()` | `401`（未登录，业务接口的正常响应） |
| HTTPX 带同一组 Cookie | `403 Forbidden`（被 ESA 拦在业务接口之前） |

拿到 `401` 说明请求已经穿过 ESA 打到了业务层。两者唯一的差别是 TLS/HTTP2 握手
指纹：ESA 认的是 Chrome 的指纹，HTTPX 换多少请求头、补多少 Cookie 都过不去。

由此推翻两个此前的判断：

- 不是「WAF Cookie 没拿全」——三个 Cookie 都拿到了，页面挑战也确实通过了。
- 不是「代理出口被限流」——浏览器走的是同一个代理出口，它拿到了 `401`。

参考项目 `millylee/anyrouter-check-in` 用 HTTPX 能成功，推测是因为它跑在 GitHub
Actions 的出口上、没有命中同一条策略，不代表 HTTPX 这条路本身更正确。**它值得
参考的是「只存 session Cookie、WAF Cookie 每次动态获取」这个认证模型，不是它的
HTTP 客户端选型。**

## 8. 最终实现

AnyRouter 现在的流程：

```text
读取 checkin_sites.json 的 cookies.session
    ↓
启动临时浏览器（无 profile）
    ↓
访问 /login，等 ESA 挑战真正跑完
    ↓
把 session Cookie 注入这个临时上下文
    ↓
页内 fetch /api/user/self
    ↓
页内 fetch POST /api/user/sign_in
    ↓
页内 fetch /api/user/self 取余额
    ↓
关闭浏览器
```

### 8.1 Cookie 配置

`tools/checkin_sites.json` 里每个 AnyRouter 账号：

```json
{
  "cookies": { "session": "真实 session 值" },
  "api_user": "你的用户 ID",
  "session_cookie": "session"
}
```

注意 `session_cookie` 存的是 **Cookie 的名字**（默认 `"session"`），不是它的值。
这个字段名有歧义，实际使用时踩过一次：把 444 字符的 session 值填进了
`session_cookie`，`cookies` 仍是 `{}`，脚本按「未配置」提前停止，看起来像没登录。
**值放 `cookies.session`，名字放 `session_cookie`。**

脚本现在会自己纠正这种误配：`session_cookie` 超过 40 个字符就认定填的是值
（Cookie 名字不会那么长，`"session"` 才 7 个字符），自动搬到 `cookies.session`
并打印一行提醒。已经填对的不会被覆盖。

`tools/checkin_sites.example.json` 里也补上了这三个字段的占位说明，避免新装一次
重踩同一个坑。

`cookies` 也支持完整 Cookie 字符串：

```json
"cookies": "session=真实值"
```

真实 Cookie 值不写入本文档，`tools/checkin_sites.json` 已被 gitignore。

### 8.2 WAF 就绪判定

只等 Cookie 出现是不够的——`acw_tc` / `cdn_sec_tc` / `acw_sc__v2` 是挑战页自己
下发的。现在要同时满足两个条件才算预热成功：

1. 三个 WAF Cookie 都拿到。
2. 页面确实通过了挑战。判据抄参考项目的 `wait_for_site_ready`：
   - 正文不含 `请进行验证` / `为了更好的访问体验` / `访问受限` / `访问验证` /
     `滑块验证` / `Access denied` / `verify you are human` / `aliyun_wa`；
   - 且没有可见的 captcha / slide iframe、`.nc-container`、`#nocaptcha`；
   - 且页面有可见的 `a` 或 `button`。

预热结果用 `WafWarmup(cookies, user_agent, passed)` 返回，把「Cookie 没下发」和
「Cookie 下发了但挑战没过」分成两种失败原因——这两者的处置完全不同。

### 8.3 不使用 HTTPX

模块已不再 `import httpx`，`_httpx_client` / `_httpx_call` 已删除。有单元测试锁
住这条约束，避免以后又被改回去。

### 8.4 Cookie 注入顺序

必须**先过 WAF、再注入 session**。反过来会把登录态暴露给挑战页那一跳。有单元
测试锁住顺序。

### 8.5 401、403、429 的区分

| HTTP 状态 | 脚本判定 | 含义 |
|---|---|---|
| `401` | 需要登录 | `session` 已失效或未配置 |
| `403` | 失败 | WAF 未通过或限流，**不要**当成账号失效 |
| `429` | 失败 | 请求频率过高 |
| `5xx` | 失败 | 服务端错误 |

### 8.6 AgentRouter

见第 12 节。

### 8.7 「今日已签到」怎么判

AnyRouter 重复签到时 `POST /api/user/sign_in` 返回：

```json
{"message":"","success":true}
```

和首次成功**完全一样**，响应体里没有任何可区分的信息。所以只能比对额度：

- 签到前的 `/api/user/self`（这次调用本来就有，用来取 `api_user`）
- 签到后的 `/api/user/self`（本来就有，用来取余额）

两者的原始 `quota` 值相等 → 判「今日已签到」。

只在**完全相等**时才判，额度变少不判：变少说明期间有消耗，那种情况下签到到底
成没成不好说，保留「签到成功」这个更安全的默认值。

比对发生在**同一次运行内**的两次调用之间，所以两次运行之间产生的消耗不会干扰
判定。实测 anyrouter-2 跨运行余额从 2931.88$ 掉到 2928.18$，仍能正确判出已签到。

### 8.8 日常运行

**先看清楚运行时机**：AnyRouter 按 UTC 日重置，本地 **08:00 之前跑会白跑**
（接口返回成功但不发放，见 12.12）。AgentRouter 本地 0 点后即可，所以统一排在
本地 08:00 之后跑一次，两个站都能覆盖。

**失败了不要连着重试。** AnyRouter 的每次运行包含一整套 WAF 预热导航加 3 次
API 调用，403 期间的重试会给限流计数器续命。实测窗口超过 37 分钟、不到 2.5 小时
（见 12.15），遇到 403 隔两小时以上再试一次即可。

单账号测试：

```powershell
python tools\daily_checkin.py --only anyrouter-1 --verbose
```

默认执行（只处理两个 AnyRouter 账号，串行，账号间延迟 5 秒）：

```powershell
python tools\daily_checkin.py --verbose
```

任务计划入口：

```powershell
tools\daily_checkin.cmd
```

日志：`logs/daily_checkin.log`。退出码：全部成功 0，有账号失败非 0。

## 9. 验证结果

### 9.1 语法与单元测试

```powershell
python -m py_compile tools\daily_checkin.py
python -m unittest discover -s tests -p "test_*.py"
```

结果：`Ran 75 tests — OK`（原 33，新增 42）。

新增覆盖：

- ESA 挑战页文案识别。
- **Cookie 齐全但仍停在验证页 → 判定未通过**（这条就是 403 的根因场景，
  修复前会误判为成功）。
- 挑战页先出现、随后就绪的重试路径。
- 页面探测抛异常时一律判未通过。
- AnyRouter 不得使用 HTTPX。
- session 注入必须在 WAF 预热之后。
- 注入的 Cookie scope 到站点 host、`path=/`、`secure`。
- 额度数值提取：跨 `quota` / `balance` / `remain_quota` 三个字段名，
  bool 不算数值（`bool` 是 `int` 的子类，不挡掉会把布尔字段当额度），
  空 body / 坏 JSON 返回 `None`。
- 额度相等判「今日已签到」，额度变少不判（保留 OK 这个安全默认值）。
- `session_cookie` 填成值时能自动纠正，且不覆盖已经填对的 `cookies`。
- 示例配置里必须有 `cookies.session` / `session_cookie` / `api_user` 三个字段。
- 示例配置里不得出现真凭据**值**。判据从「不许出现 session/cookie 字样」
  改成「任何 40 字符以上、纯 `[A-Za-z0-9._+/=-]` 的字符串都算真凭据」——
  前者是登录态还在 profile 里时的前提，现在 AnyRouter 的认证就是配置里的
  session，字段名必然出现。

## 10. 后续维护注意事项

1. `session` 过期时只更新对应账号的 `cookies.session`。值放 `cookies` 里、
   名字放 `session_cookie`；填反了脚本会自动纠正并提醒，但别依赖这个。
2. **不要把 AnyRouter 的 API 调用改成 HTTPX / requests / curl。** 已实测被 ESA
   按 TLS 指纹拦截，返回 403。网络栈必须是浏览器自己的。
3. 不要把 WAF Cookie 固定写进配置，它每次都要动态获取。
4. 不要把 AnyRouter 改回 profile 模式，它现在不需要保存登录态。
5. 遇到 403 / 429 先等待，不要连续重试——每次重试都在续限流窗口。
6. 两个账号必须串行，账号之间有 5 秒延迟。
7. AgentRouter 暂时保持关闭，后续单独重新设计每日重新登录逻辑。
8. 当前独立项目不读取、不修改 Bot 项目的登录态。

## 11. 最终结论

AnyRouter 的正确自动签到模型是：

```text
session Cookie      负责账号认证（固定保存）
临时浏览器          负责过 ESA 挑战并动态获取 WAF Cookie
浏览器页内 fetch    负责发 API 请求（关键：必须是浏览器的网络栈）
串行 + 延迟         负责降低限流风险
```

最容易走错的一步是最后那条：认证模型抄对了，但把 HTTP 客户端换成 HTTPX，就会
稳定拿到 403，而且现象（浏览器能正常打开、页面显示已登录）会把人误导到「登录态
失效」或「代理被封」上去。

## 12. AgentRouter

### 12.1 站点规则

- **每天要退出后重新登录**，重新进入时才计签到。刷新页面不算。
- **没有独立的签到接口**：查 `/api/user/self` 本身就会触发签到，配置里
  `checkin_path` 留空。
- 登录页提供三种方式：`Continue with GitHub`、`Continue with LinuxDO`、
  `Sign in with Email or Username`。

参考项目 `millylee/anyrouter-check-in` 的 provider 定义和实测一致：
`sign_in_path=None`、`user_info_path='/api/user/self'`、`use_proxy=True`。

### 12.2 走不通的路：LinuxDO OAuth

2026-08-27 实测（全程有回滚保护，旧会话已恢复）：

| 尝试 | 结果 |
|---|---|
| 直接 `goto /oauth/linuxdo` | 落到 `/login?expired=true`，不自动跳 |
| 走 `/login` 点 “Continue with LinuxDO” | 开**弹窗**到 `connect.linux.do/oauth2/authorize?...&state=...` |
| 等弹窗 24 秒 | URL 不变、body 全空、不回跳，主页面仍未登录 |

profile 里 linux.do 的登录态是**有效的**——`_t`（Discourse 认证 token）和
`cf_clearance` 都在，Playwright 确认会发往 `connect.linux.do`。卡点不是登录态
过期，而是授权页在 headless 下渲染不出来。

### 12.3 真正的拦路虎：`/api/user/self` 上的人工滑块

改用表单登录后，登录本身**成功了**（控制台正常显示已登录用户），但
`/api/user/self` 以 HTTP 200 返回了一整页阿里云验证 HTML。

直接把浏览器导航到该 API 地址，看清了它是什么：

```text
访问验证
别离开，为了更好的访问体验，请进行验证，通过后即可继续访问网页
请按住滑块，拖动到最右边
```

是**人机滑块**，不是能自动跑完的 JS 挑战。做了三组对照，全部命中滑块：

| 变量 | 结果 |
|---|---|
| 页内合成 `fetch` | 滑块页 |
| **站点前端自己发的 XHR** | 滑块页 |
| 无头 / 有头浏览器 | 都是滑块页 |
| 走代理 / 直连 | 都是滑块页 |

所以和「谁发请求」「什么指纹」「什么出口 IP」都无关——是这个接口对**没有放行
记录的浏览器上下文**一律要人工滑块。

### 12.4 采用的方案：持久化 profile + 每天只清登录 Cookie

临时浏览器一律吃滑块，持久化 profile 不吃（原因见 12.7.1）。于是：

- **用持久化 profile**（不是临时浏览器）——临时浏览器会触发滑块，见 12.7.1。
- 「退出」不是丢掉整个 profile，而是**精确清掉登录 Cookie**（`session`），
  同域的 WAF 放行 Cookie 全部保留。整域清会把人工换来的放行一起清掉，
  下次又得人工，自动化就断了。
- 清完再用用户名/密码重新登录，满足「退出后重新登录」这条规则。

流程：

```text
打开持久化 profile
    ↓
只清 session Cookie（= 退出），保留 WAF 放行
    ↓
访问根路径，等 ESA 挑战跑完
    ↓
/login 点出邮箱表单，填 username / password 提交
    ↓
等 session 出现且已离开 /login
    ↓
_settle（过应用侧 WAF + 抓 New-Api-User）
    ↓
页内 fetch /api/user/self（这一步即完成签到）
```

命中滑块页时会重新预热重试一次，仍不过则报：

```text
需要人工完成一次滑块验证：python tools/daily_checkin.py --login agentrouter-1
```

`interactive_login` 里本来就有这一步——它会另开一个真实浏览器窗口指向该 API
地址，让人把滑块滑完。

### 12.5 配置

```json
{
  "name": "agentrouter-1",
  "kind": "relogin",
  "base_url": "https://agentrouter.org",
  "checkin_path": "",
  "username": "邮箱或用户名",
  "password": "密码",
  "enabled": true
}
```

OAuth 注册的账号可以在个人设置里绑定密码，绑完就能走表单登录。

**又一个填错字段的坑**：实际配置时把 `邮箱/密码` 填进了 `oauth_path`。那个字段
存的是 OAuth 入口路径（如 `/oauth/linuxdo`），一定以 `/` 开头。脚本现在会认出来
——不以 `/` 开头、含 `@`、含 `/` 的值判定为凭据，按**第一个** `/` 切开搬到
`username` / `password`（密码本身可能含 `/`），并打印提醒。已填对的不覆盖。
这和 8.1 节 `session_cookie` 那个坑是同一类。

`checkin_site` 的路由：AnyRouter 走 `_checkin_anyrouter`；配了 `password` 的走
`_checkin_agentrouter`；都没配的仍走原来的 profile + OAuth 重登路径作为退路。

密码不进日志，有测试锁住 `_login_with_password` 里所有 `print` 不含凭据。

### 12.6 顺带修掉的回归

`_relogin` 的失败回滚 `_restore_site_cookies` 在 08-26 那次重构里被删掉了。
没有它，一次失败的重登会把原本还能用的会话清空，把「今天没签上」放大成
「必须人工重新登录」。已补回，12.2 节的几次 OAuth 实测都靠它回滚了旧会话。

同时把「返回的是 WAF 验证页」这个判定补回 `classify_response`——也是 08-26 删掉
的，删掉后命中滑块只会吐一整页原始 HTML 到日志里。补回的位置在状态码判定**之后**，
避免 AnyRouter 的 403（body 里也有 `aliyun_wa`）被误报成需要人工登录。

### 12.7 「今日已签到」怎么判：查系统日志

先记一次误判。14:28 和 14:29 两次运行都报「签到成功」，余额都是 484.63$ 没变：

```text
2026-08-27 14:28:45 agentrouter-1: 签到成功 | 余额 484.63$
2026-08-27 14:29:27 agentrouter-1: 签到成功 | 余额 484.63$
```

后来在站点的「使用日志」页面看到，当天的签到其实是 **09:01:54** 由别处完成的：

```text
2026-08-27 09:01:54  系统  每日签到成功，增加额度 ＄25.000000 额度
```

也就是说那两次「签到成功」都是**假阳性**。当时判断「AgentRouter 没法判已签到」
是错的——余额差确实用不了（查 `/api/user/self` 就等于签到，拿不到签到前的状态），
但**系统日志**可以。

接口：

```text
GET /api/log/self?p=1&page_size=20&type=4&start_timestamp=<当天0点>&end_timestamp=<当天23:59:59>
```

`type=4` 是「系统」类日志，返回：

```json
{"data": {"items": [
  {"id": 636, "user_id": 10001, "created_at": 1787792514, "type": 4,
   "content": "每日签到成功，增加额度 ＄25.000000 额度", "username": "linuxdo_10001"}
]}}
```

判定规则：取当天所有签到记录里**最早**的时间戳，早于本次运行的开始时间就说明
「本次运行之前就签过了」，判 ALREADY；否则是本次运行签上的，判 OK。

注意 content 里的 `＄` 是**全角**美元符号，所以只匹配「签到」两个字，不碰金额。

修正后的实际输出：

```text
agentrouter-1: 今天已签过 | 余额 484.63$ | 今日已签到（系统日志显示本次运行前已签过）
```

### 12.7.1 更正：滑块和「人工放行 Cookie」无关


一度以为「能跑通是因为 profile 里存着之前人工滑块换来的放行 Cookie」。查过
profile 后发现**不成立**：`agentrouter_1` 的 profile 里 `agentrouter.org` 域下
只有 `session`，`acw_tc` / `acw_sc__v2` 一个都没有。`acw_tc` 是每次运行时
`_warm_site` 现拿的。

真正的差别是**浏览器启动方式**：

| 启动方式 | `/api/user/self` |
|---|---|
| `_launch`（持久化 profile + 真实 Edge channel） | 正常返回 |
| `_open_temp_page`（临时浏览器 + 全新 context） | 滑块页 |

12.3 节那几组对照（有头/无头、代理/直连、合成 fetch / 前端 XHR）全都是在**临时
浏览器**里做的，所以才一律命中滑块。持久化 profile 不吃这一套。

结论修正：AgentRouter 用持久化 profile 不是为了保存人工放行，而是因为**临时
浏览器本身就是触发滑块的原因**。

### 12.9 配置文件的两个坑

**坑一：值填错字段。** 已经踩过两次，脚本都做了自动纠正并打印提醒：

| 填错的位置 | 应当填在 | 识别依据 |
|---|---|---|
| `session_cookie` 填了 session 的值 | `cookies.session` | 长度 > 40（Cookie 名字不会那么长） |
| `oauth_path` 填了 `邮箱/密码` | `username` / `password` | 不以 `/` 开头、含 `@`、含 `/` |

自动纠正是兜底，不是正路——发现提醒时应该回头把配置改对。

**坑二：JSON 缺逗号。** 补 `agentrouter-2` 时踩到：

```json
    "oauth_path": "/oauth/linuxdo",
    "enabled": true          ← 少了逗号
    "username": "...",
    "password": "..."
```

报错是 Python 原始的 `JSONDecodeError: Expecting ',' delimiter: line 57 column 5`，
能定位但不够直白。新增字段时要么加在末尾（记得给前一行补逗号），
要么插在中间（自己那行末尾带逗号）。

### 12.12 两个站的「每日」口径不一样

anyrouter-1 没有消耗，数据最干净：

| 时刻（本地 CST） | 换算 UTC | 余额 |
|---|---|---|
| 08-27 12:47 | 08-27 **04:47** | 756.83 → 781.83（+25） |
| 08-28 06:47 | 08-27 **22:47** | 781.83（无变化） |

两次运行落在**同一个 UTC 日**内。推断 AnyRouter 的每日重置按 UTC 计算，
即本地时间**早上 8 点**才跨日。

对照 AgentRouter：08-27 09:01 CST 签过，08-28 06:47 CST 又发放成功——两者同属
UTC 08-27，说明它按**本地日**计算。

所以脚本并没有误判：站点确实认为「本 UTC 日已领过」，`sign_in` 返回
`{"message":"","success":true}` 但不发放，余额不变，判「今天已签过」符合站点状态。
只是「今天」的定义和本地日历不同。

**运维含义**：AnyRouter 的定时任务应安排在**本地 08:00 之后**，
否则会重复领取前一个 UTC 日的额度（实际拿不到）。AgentRouter 不受此限制
（它 0 点过后就能重新登录签到）。

**跨日后复测（08-28 08:06，UTC 刚跨日 6 分钟）验证了这个推断**：

```text
anyrouter-1: 签到成功 | 余额 806.83$  | 签到成功，获得 $25 额度
anyrouter-2: 签到成功 | 余额 2843.53$ | 签到成功，获得 $25 额度
```

anyrouter-1 无消耗，干净地 781.83 → 806.83（+25）。紧接着再跑一次：

```text
anyrouter-1: 今天已签过 | 余额 806.83$ | 今日已签到（额度未变化）
```

完整闭环（首次签到 → 重复签到）验证通过。

### 12.12.1 `message` 字段是更直接的信号

跨日复测时注意到 `sign_in` 的响应有区别：

| 情形 | `sign_in` 响应 |
|---|---|
| 首次签到 | `{"success":true,"message":"签到成功，获得 $25 额度"}` |
| 重复签到 | `{"success":true,"message":""}` |

比 8.7 节写的「响应体区分不出来」要好一些——当时只在重复签到的状态下观察过，
没见过首次签到的响应。

但没有把它改成主判据：空串也可能只是站点没给文案，单凭它下结论不稳。现在的做法
是拿它做**否决**——`message` 非空即确定本次签到成功，不再看额度；只有 `message`
为空时才用额度差判断。额度差仍是主判据。

### 12.15 AnyRouter 被限流

导航到 API 地址看到了明确原因：

```text
403 Sorry, you have been blocked
Denied by http_ratelimit
RuleID: 21888958
```

是**限流**，不是结构性封禁。对照实验：

| 变量 | 结果 |
|---|---|
| 临时浏览器 / 持久化 profile | 都 403 |
| 走代理 / 直连 | 都 403 |
| WAF 预热本身 | **正常通过**（三个 Cookie 齐全、页面就绪） |

代理和直连结果相同，说明限流不只按 IP 算，很可能还按 session / 账号维度。

**触发原因是访问频次，不是代码问题**——前一天同样的代码在 08:07 正常签到成功。
当天为了排查 AnyRouter 的行为，在正常那一轮之外额外跑了 3 轮诊断，每轮都包含
WAF 预热的多次页面导航加 API 调用，把额度耗掉了。

**教训**：AnyRouter 的排查要克制。每次「跑一下看看」的成本不是一个请求，而是
一整套预热导航 + 3 次 API 调用。403 期间继续重试只会延长限流窗口。

**处理方式**：等限流窗口过去后重跑即可。UTC 日到次日本地 08:00 才结束，
当天有充足的补签时间。

### 12.16 第四日验证（2026-08-30 08:35）：暴露两个健壮性 bug

这一轮跑到一半崩了：

```text
anyrouter-1:   签到成功 | 余额 856.83$  (+25)
anyrouter-2:   签到成功 | 余额 2264.47$ (+25)
agentrouter-1: 签到成功 | 余额 559.63$  (+25)
agentrouter-2: 需要人工重新登录 | 登录页找不到邮箱/用户名表单
agentrouter-3: Traceback —— Page.goto: net::ERR_TIMED_OUT at /login
agentrouter-4: 没跑到
```

**站点侧全是好的**：AnyRouter 的 session 第三天仍有效，AgentRouter 的 profile
第三天仍免滑块。失败是网络抖动（代理拥塞）加上脚本自身不够健壮。

#### bug 1：一个账号的异常打断整轮

`checkin_site` 的两条早退分支写在 `try` 之外：

```python
if _is_anyrouter(site):
    return _checkin_anyrouter(...)      # 异常直接冲到 main()
if site.password:
    return _checkin_agentrouter(...)    # 同上
```

只有下面那条 profile + OAuth 的老路径有 `except Exception`。所以
agentrouter-3 的导航超时一路抛到 `main()`，agentrouter-4 根本没执行。

已修：两条分支各自 `try/except`，失败转成 `FAILED` 结果继续跑下一个账号。

#### bug 2：崩溃导致已完成的结果全部丢失

`write_log` 在主循环**之后**调用，循环抛异常就永远走不到。当天前 3 个账号
明明成功了，`logs/daily_checkin.log` 里却一条 08-30 的记录都没有。

已修：主循环包 `try/finally`，`write_log` 放进 `finally`。

#### 顺带加的重试

`/login` 导航超时和「找不到邮箱表单」都是网络抖动导致的偶发失败，一次不成不代表
账号有问题。抽出 `_open_login_page()`，导航 + 点出表单整体重试 3 次，失败信息
带上最后一次的原因和重试次数。

补跑验证（修复后）：

```text
08:50:09 agentrouter-2: 签到成功 | 余额 369.56$
08:51:01 agentrouter-3: 签到成功 | 余额 250.00$
08:51:36 agentrouter-4: 签到成功 | 余额 275.00$
```

三个都一次过，当天六个账号最终全部签到成功。

**教训**：无人值守脚本的失败模式不只是「某个账号签不上」，还有「一个账号把整轮
带走」和「结果没落盘」。前者让后面的账号静默漏签，后者让人事后完全查不到发生了
什么——两个都比单账号失败更难发现。

### 12.17 已知风险与备选方案

**最大的未知数是持久化 profile 还能「免滑块」多久。** 已连续两天正常
（08-28、08-29），暂未出现失效迹象。
如果哪天 profile 也开始吃滑块，就得人工滑一次
（`python tools\daily_checkin.py --login agentrouter-1`），届时该考虑换更强的
反检测方案。

备选方案：`jiang7f/checkin-agentrouter`（专做 AgentRouter）。

| | 该项目 | 本项目当前实现 |
|---|---|---|
| 触发签到 | 每次重做 **GitHub** OAuth | 每次清 session 后重新密码登录 |
| 浏览器 | `cloakbrowser`（反指纹） | Playwright + 真实 Edge channel + stealth |
| 过滑块 | 靠 cloakbrowser 规避 | 靠 profile 里人工滑一次的放行 |
| 每账号保存 | GitHub 登录态 | AgentRouter profile |
| 已签到判定 | 签到前后余额对比 + 关键词 | 系统日志 type=4（见 12.7） |
| 目标平台 | macOS + uv | Windows |

它的关键差异是 `cloakbrowser`——反指纹浏览器能直接规避滑块，因此不依赖任何人工
步骤。如果放行 Cookie 被证实会频繁过期，换成 cloakbrowser 是正确的下一步；它同时
也可能顺带解决 12.2 里 LinuxDO 授权页渲染空白的问题。

注意它走的是 **GitHub** OAuth，而本项目之前试的是 LinuxDO。

另一个备选：`dctx-team/Regular-inspection`。它同时覆盖 AnyRouter 和 AgentRouter，
主分支支持 Cookies + 邮箱密码，测试分支 `feature/cloudflare-optimization-2025`
支持 GitHub / Linux.do OAuth。

对本项目而言它比 `jiang7f/checkin-agentrouter` 更贴合：**同样是 Playwright**，
不需要换成 cloakbrowser，也就不用改技术栈或换平台（那个项目是 macOS + uv）。
它的反检测是在 Playwright 上加一层 JS 特征伪装和启动参数优化——去掉
`navigator.webdriver`、伪装 plugins / languages / permissions、模拟 chrome 对象等，
自称普通 WAF 通过率 98%+。本项目现在只用了 `playwright-stealth`，如果 12.8 说的
放行 Cookie 被证实会频繁过期，把它那套反检测搬过来是成本最低的下一步。

它还有一个「OAuth → Cookies 智能降级」：认证成功后缓存 session 24 小时，命中缓存
就跳过浏览器直接发 HTTP 请求。这个思路对 AnyRouter 没意义（我们已经是纯 Cookie 模式），
对 AgentRouter 也不适用（每天必须重新登录才计签到）。
